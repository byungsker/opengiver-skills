# 웹 UI 폼 검증 패턴

웹 UI 폼을 새로 만들거나 수정·검토할 때 사용한다. 목적은 새 UI를 고립된 예제로 만드는 것이 아니라 현재 프로젝트의 `design-system primitives`, 폼 상태 관리, 오류 표시, API 경계를 먼저 찾아 재사용하는 것이다. 기존 프로젝트 규칙과 `backend authorization`이 이 문서보다 우선한다.

## 적용 전 라우팅

다음 순서를 지킨다.

1. 프로젝트의 `DESIGN.md`, 디자인 토큰, 컴포넌트 라이브러리, 폼 primitive, 타이포그래피, 간격, focus/error 스타일과 관련 화면을 찾는다.
2. 프로젝트에 계획·리뷰·QA 절차가 있으면 목표, 수용 기준, 상태와 실제 QA 증거를 그 절차에 연결한다. 특정 에이전트나 명령어가 설치되어 있다고 가정하지 않는다.
3. 같은 프로젝트에서 기존 `form`, `field`, `validation schema`, `error copy`, `loading indicator`, `success feedback`, `retry pattern`과 관련 테스트를 검색한다. 새 primitive나 새 상태 명칭은 기존 패턴이 없을 때만 최소 범위로 제안한다.
4. 기존 패턴이 없으면 `기존 패턴 없음`이라고 기록하고, 선택한 표준 primitive와 접근성 규칙의 근거를 남긴다. `legacy HTML`을 복사하거나 제품별 문구를 추측하지 않는다.

## 구현 전 계약

먼저 필드와 경계를 표로 정리하고, [상태 매트릭스](references/state-matrix.md)를 필요한 범위에서 채운다.

- 입력별 형식·필수·길이·범위 규칙과 표시 시점을 구분한다. 입력 중 즉시 표시할 오류와 blur/submit 뒤 표시할 오류를 프로젝트의 기존 관례에 맞춘다.
- `cross-field` 규칙은 관련 필드 그룹과 폼 수준에 연결한다. 한 필드의 오류처럼 보이게 만들어 사용자가 원인을 추측하게 하지 않는다.
- `client validation`은 빠른 형식·범위 피드백을 담당하고, `policy/domain` 오류와 권한·소유권 판정은 `backend/API`를 권위 있는 기준으로 둔다. view에서 `Firestore document`나 업무 규칙을 임의로 조립하지 않는다.
- API 응답의 성공 여부, `field error`, `form error`, `policy/domain error`, 네트워크/시간 초과를 구분하여 기존 오류 계약과 사용자 피드백으로 매핑한다. HTTP 성공만으로 업무 성공을 단정하지 않는다.
- 제출에는 중복 클릭, 느린 응답, 재시도, `stale response`를 포함한다. 진행 중 요청은 중복 제출을 막되, `disabled CTA`만으로 상태나 오류를 설명하지 않는다.

## 상태별 UI 규칙

최소한 다음 상태를 설계하고 실제 화면에서 관찰 가능하게 만든다.

- 빈 상태와 `pristine` 상태: 무엇을 입력해야 하는지, 필수 여부와 다음 행동을 알려 준다. 값이 없다는 사실만 오류로 표시하지 않는다.
- 편집 중과 동기 검증: 입력을 지우거나 고칠 때 기존 오류가 갱신·제거되는 시점을 일관되게 한다.
- 검증 실패: 오류를 해당 `field` 또는 `group` 가까이에 평문으로 표시하고, 오류 요약이 있다면 같은 내용을 중복 낭독하지 않도록 한다.
- 비동기 검증과 제출 중: `aria-busy`, 진행 상태, 재입력 가능 여부를 표시한다. 버튼 비활성만 남기지 말고 상태 영역 또는 설명을 제공한다.
- 성공: 제출 완료와 다음 가능한 행동을 명확히 표시한다. 성공을 단순히 버튼 문구의 순간 변경으로만 알리지 않는다.
- 실패와 재시도: 입력값과 사용자가 작성한 맥락을 보존하고, 재시도 범위와 원인을 설명한다. 재시도 후 동일 오류와 새 오류를 구분한다.
- 경계·정책·도메인 오류: 서버의 권위 있는 결과를 `field/form` 수준에 맞게 표현하고, 권한 부족이나 충돌을 `validation` 오류인 것처럼 숨기지 않는다.
- 중복·`stale` 제출: 한 번만 처리되어야 하는 작업은 `idempotency` 또는 요청 식별 전략을 확인하고, 이전 응답이 최신 입력을 덮어쓰지 않도록 한다.

## 접근성 및 상호작용 확인

- 모든 입력에 연결된 표시용 `label`과 필요한 설명을 제공한다. 오류는 `aria-describedby`로 연결하고 잘못된 `field`에는 `aria-invalid="true"`를 사용한다.
- 오류가 동적으로 나타날 때 `role="alert"` 또는 `aria-live`를 기존 프로젝트의 방식에 맞게 사용한다. 같은 메시지를 여러 live region에서 반복하지 않는다.
- `submit` 후 첫 오류 `field` 또는 오류 요약으로 `focus`를 이동하되, 사용자가 이미 이동한 `focus`를 비동기 응답이 빼앗지 않게 한다. 키보드만으로 입력·수정·재시도·성공 후 다음 행동이 가능해야 한다.
- 오류와 상태를 색상, 아이콘, `disabled` 상태 하나로만 전달하지 않는다. 충분한 텍스트, `focus`, 구조적 관계를 함께 제공한다.
- `loading` 중에도 상태의 의미를 알 수 있어야 하며, 성공·실패·재시도 전환에서 `screen reader`와 키보드 사용자의 위치가 예측 가능해야 한다.

## 검증과 QA

구현 전 정한 `validation-pattern audit criterion`을 프로젝트의 수용 기준과 QA 기록에 포함한다.

시각 또는 검토 QA로 넘어가기 전에 다음을 순서대로 수행한다.

1. 상태 매트릭스, 수용 기준, evidence와 stop condition을 다시 확인한다.
2. 실제 브라우저 또는 프로젝트의 UI 검증 도구로 화면 크기와 키보드 상호작용을 관찰한다.
3. 가능하면 독립 리뷰어에게 구현·상태 매트릭스·검증 증거를 제공한다. 오류 상태, 접근성 관계, backend/API 경계, retry와 stale 방지 증거를 함께 전달한다.

최소 수동 QA 시나리오는 다음을 포함한다.

- 빈 제출과 잘못된 단일 필드: `inline error`가 올바른 `field`에 나타나고 `aria-invalid`·`aria-describedby`가 연결되며, 첫 오류로 `focus`가 이동한다.
- `cross-field` 오류와 `policy/domain` 오류: 관련 `group/form`에 이해 가능한 오류가 표시되고, 권한·업무 규칙 오류가 단순 형식 오류로 축약되지 않는다.
- 느린 비동기 검증과 제출: `loading` 상태, `aria-busy` 또는 동등한 상태 설명, 중복 제출 방지, 성공 상태가 순서대로 보인다.
- 네트워크/서버 실패와 `retry`: 작성한 값이 보존되고 재시도 안내와 결과가 보이며, `disabled CTA`만 남지 않는다.
- 빠른 연속 제출과 오래된 응답: 최신 입력의 결과만 화면에 반영되고, 동일 작업이 중복 처리되지 않는다.
- 빈 목록·초기 데이터 없음·복구 가능한 `empty state`: 다음 행동과 재시도 또는 생성 경로가 설명된다.
- 키보드 및 `screen reader` 흐름: `label`, 설명, 오류, `loading`, 성공, 실패가 순서대로 탐색·낭독되고 색상만으로 상태를 구분하지 않는다.

검증 결과에는 통과·실패한 상태, 확인하지 못한 외부 `provider/runtime` 상태, `기존 패턴 없음` 기록 여부를 분리해 남긴다. 로컬 코드·테스트·브라우저 증거만으로 `backend`, `provider`, 배포, `release` 승인을 주장하지 않는다.
