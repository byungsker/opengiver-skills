# Toss Frontend Fundamentals

Toss의 공개 `Frontend Fundamentals`를 변경 가능성 중심의 코드 품질 리뷰 규칙으로 적용한다. 좋은 프론트엔드 코드는 새 요구사항을 반영하고 배포하기 쉬운 코드라는 관점에서, 아래 네 가지 기준으로 현재 코드의 변경 영향과 읽기 비용을 판단한다.

이 Skill은 `omo:frontend`의 시각 설계·성능·접근성 규칙을 대체하지 않는다. 코드 품질을 검토할 때는 이 Skill을 함께 읽고, 성능·SEO·접근성 또는 시각 동작이 요청 범위에 있을 때만 해당 `omo:frontend` 규칙셋을 추가로 적용한다.

## 근거와 범위

- 공개 문서: <https://frontend-fundamentals.com/code-quality/>
- 공개 저장소: <https://github.com/toss/frontend-fundamentals>
- 저장소의 `frontend-fundamentals-plugin`은 네 원칙을 Claude Code 리뷰 Skill과 평가 과제로 구체화한 참고 구현이다.
- 이 Skill은 원문을 대체하거나 Toss의 모든 팀 규칙을 대표한다고 주장하지 않는다. 저장소에 근거가 있는 패턴만 사용하고, 현재 프로젝트의 계약·변경 이력·테스트를 우선한다.

- [source-manifest.md](references/source-manifest.md)는 원문 스냅샷의 인덱스다. `references/source/` 아래에는 저장소의 code-quality 원문과 플러그인 실행 규칙을 파일 단위로 보존했다.
- [review-rubric.md](references/review-rubric.md)는 판정을 돕는 요약·오판 방지 레이어일 뿐 원문을 대체하지 않는다. 원칙에 근거한 finding을 만들 때는 반드시 manifest에서 해당 원문을 찾아 실제로 읽는다.
- 원문이 갱신되었는지 확인하는 작업이라면 위 저장소의 현재 파일을 다시 확인하고, 로컬 스냅샷을 최신 사실로 취급하지 않는다.

## 적용 절차

1. **검토 범위를 고정한다.** diff 리뷰인지, 지정 파일 리뷰인지, 기능 디렉터리 구조 리뷰인지 구분한다. 사용자가 요청하지 않은 전역 리팩터링으로 범위를 넓히지 않는다.
2. **원문을 라우팅한다.** [source-manifest.md](references/source-manifest.md)에서 관찰한 냄새에 대응하는 원문 문서를 고르고, 요약만 읽은 상태로 결론을 내리지 않는다. 복합 이슈라면 관련 원문을 각각 읽는다.
3. **변경 가능성의 증거를 읽는다.** 변경 파일만 보지 말고 직접 호출자·소비자·타입·테스트·설정 중 판단에 필요한 인접 코드를 확인한다. 읽지 않은 동작은 추측하지 않는다.
4. **네 기준 중 실제로 관찰된 것만 분류한다.** 하나의 냄새가 여러 기준에 걸치면 주된 변경 위험을 하나로 정하고, 보조 관점은 짧게 덧붙인다.
5. **최소 수정안을 제안한다.** 동작과 공개 API를 보존하고, 현재 변경 단위에 맞는 작은 개선을 우선한다. 수정 요청이 없으면 코드를 바꾸지 않고 리뷰만 보고한다.
6. **상충 관계를 설명한다.** 네 기준을 동시에 최대화할 수 없으므로, 왜 가독성·응집도·결합도 중 하나를 우선했는지와 어떤 위험을 남기는지 기록한다.
7. **수정했다면 검증한다.** 관련 테스트·타입 검사·린트·빌드를 변경 위험에 비례해 실행한다. UI 동작이 바뀌었다면 `omo:frontend`의 브라우저·시각 검증을 별도로 통과시킨다.

## 네 가지 기준

| 기준 | 질문 | 대표적인 관찰 신호 |
| --- | --- | --- |
| **가독성** | 코드를 위에서 아래로 읽으며 의도를 빠르게 이해할 수 있는가? | 서로 실행되지 않는 분기가 한 컴포넌트에 섞임, 구현 상세가 호출부에 노출됨, 복잡한 조건·중첩 삼항·매직 넘버·시점 이동 |
| **예측 가능성** | 이름·매개변수·반환값만으로 실제 동작을 예상할 수 있는가? | `get`·`fetch`·`calculate`에 숨은 부수 효과, 같은 종류의 함수/Hook의 반환 모양 불일치, 표준 API와 충돌하는 이름 |
| **응집도** | 함께 바뀌어야 하는 코드가 함께 바뀌도록 모여 있는가? | 기능 파일이 기술 유형별 디렉터리에 흩어짐, 같은 의미의 상수 분산, 폼의 변경 단위와 검증·상태 배치가 불일치 |
| **결합도** | 한 부분의 수정이 관련 없는 넓은 범위에 영향을 주는가? | 불필요한 Props Drilling, 한 Hook의 여러 무관 책임, 변동 가능성이 다른 기능의 과도한 공통화 |

## 리뷰 판단 규칙

- **가독성:** 분기별 동작이 다르면 별도 컴포넌트·함수로 분리하고, 복잡한 조건에는 도메인 의미가 드러나는 이름을 붙인다. 구현을 감추는 추상화는 읽는 맥락을 줄일 때만 사용한다. 간단한 조건을 객체·HOC·팩토리로 감싸 시점 이동을 늘리지 않는다.
- **예측 가능성:** 함수 이름이 약속하는 범위보다 더 많은 일을 하면 순수 계산·조회와 저장·로깅·추적·네비게이션을 분리하거나 이름에 동작을 드러낸다. 같은 종류의 Hook과 검증 함수는 프로젝트의 일관된 반환 계약을 따르며, 필요한 경우 판별 가능한 Union을 사용한다.
- **응집도:** 함께 수정되는 파일을 기능·도메인 경계에 가깝게 배치하고, 여러 위치에서 같은 의미로 함께 바뀌는 값만 공통 상수로 둔다. 폼은 필드가 독립적으로 바뀌는지, 필드들이 하나의 흐름으로 함께 바뀌는지에 따라 필드 단위와 폼 전체 단위 중 선택한다.
- **결합도:** 책임을 좁히고, 중간 컴포넌트가 사용하지 않는 값을 전달하기만 한다면 조합(`children`)을 먼저 검토한다. 깊고 실제로 공유되는 상태에만 Context를 고려한다. 페이지별 요구가 달라질 가능성이 크면 중복을 허용해 공통 코드의 변경 폭을 줄인다.

## 반드시 피할 오판

- 숫자·문자열·조건을 의미 없이 모두 상수화하지 않는다. 이름이 맥락을 실제로 줄이거나 함께 변경되어야 할 때만 추출한다.
- Props가 존재한다는 이유만으로 Context나 전역 상태를 도입하지 않는다. 컴포넌트의 공개 역할을 설명하는 Props는 결합도가 아니다.
- 비슷해 보인다는 이유만으로 Hook·컴포넌트를 공통화하지 않는다. 미래 요구사항을 모두 수용하는 옵션·플래그·팩토리를 추가하지 않는다.
- 주석이나 JSDoc으로 숨은 부수 효과를 정당화하지 않는다. 다만 기존 API 계약을 깨지 않는 선에서 호출부 또는 이름에 동작을 명시한다.
- 성능·접근성·보안·기능 정확성 문제를 코드 품질 원칙으로 덮어쓰지 않는다. 해당 문제가 보이면 별도 검증 결과와 함께 보고한다.

## 보고 형식

리뷰 결과는 다음 순서를 지킨다.

```markdown
## 요약
변경 가능성에 대한 1~2문장 요약

## 핵심 문제
- **[기준][심각도]** `path/to/file.tsx:line` — 관찰한 코드와 변경 영향
  - 근거: 현재 코드에서 확인한 사실
  - 원문: 읽은 `references/source/...` 문서와 대응되는 원격 문서
  - 제안: 동작을 보존하는 최소 수정

## 트레이드오프
우선한 기준, 허용한 중복·추상화, 남은 위험

## 검증과 제한
실행한 검사, 실행하지 못한 검사, 읽지 않은 범위
```

심각도는 `Critical`(변경 범위·오류 위험이 직접 크고 수정 우선순위가 높음), `Warning`(유지보수 위험이 확인됨), `Suggestion`(선택적 개선)으로 구분한다. 근거가 부족하면 finding을 만들지 말고 `확인 불가` 또는 추가로 읽어야 할 파일을 적는다.

## 출처 비교 모드

사용자가 Toss 문서와 저장소를 비교해 달라고 하면, 렌더링된 웹 문서는 네 원칙의 공개 요약과 링크 확인에 사용하고, 저장소는 원문 분석의 정본으로 사용한다. 이 Skill에서는 저장소 내용을 `references/source/`에 고정한 뒤, 실제 판단 때 관련 원문을 lazy-load한다. 결론과 finding에는 사용한 원문 경로와 저장소 커밋 또는 시점을 남긴다.
