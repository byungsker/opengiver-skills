# Toss Frontend Fundamentals 리뷰 점검표

이 문서는 `toss-frontend-fundamentals` Skill이 실제 코드를 읽을 때 사용하는 판정용 요약·오판 방지 레이어다. 원문을 대신 읽어주는 문서가 아니므로, 원칙에 근거한 finding을 만들기 전에는 [source-manifest.md](source-manifest.md)에서 대응하는 원문을 찾아 읽는다. 모든 항목을 기계적으로 적용하지 말고, 현재 변경 단위와 소비자를 읽은 뒤 관찰된 항목만 보고한다.

## 1. 가독성

### 확인할 것

- 동시에 실행되지 않는 역할·권한·상태 분기가 한 컴포넌트에 섞여 있지 않은가?
- 호출부가 구현 상세를 지나치게 알아야 의도를 이해할 수 있지 않은가?
- 쿼리 파라미터·상태·API·이벤트처럼 서로 다른 종류의 로직이 하나의 거대한 Hook이나 함수에 몰려 있지 않은가?
- 복잡한 조건, 매직 넘버, 중첩 삼항이 이름 없이 사용되지 않는가?
- 코드의 실행 흐름을 따라가기 위해 위아래·파일 사이를 반복해서 이동해야 하지 않는가?

### 적합한 개선

- 서로 다른 동작을 별도 컴포넌트·함수로 나누고, 각 분기의 맥락을 줄인다.
- 구현을 감싸는 함수·Wrapper·컴포넌트는 호출부가 “무엇을 하는지” 바로 읽게 할 때만 둔다.
- 조건에는 `canInvite`, `isEligible`처럼 도메인 의도를 담은 이름을 사용한다.
- 같은 의미로 함께 바뀌는 값에는 의미 있는 상수를 사용한다.
- 단순한 로직은 펼쳐서 읽히게 하고, 필요하면 early return·`if`·`switch`·조회 객체를 사용한다.

### 피할 개선

- 주석을 늘려 복잡한 분기·삼항을 유지하기
- “미래 확장성”을 위해 HOC·팩토리·깊은 계층을 추가하기
- 한 줄짜리 조건까지 이름을 붙여 오히려 읽기를 끊기

## 2. 예측 가능성

### 확인할 것

- `getX`, `fetchX`, `calculateX`에 **숨은 부수 효과(hidden side effects)**인 저장·로깅·추적·네비게이션·캐시 변경이 들어 있지 않은가?
- 같은 종류의 API Hook이 하나는 Query 객체를, 다른 하나는 `data`만 반환하는 식으로 계약이 갈리지 않는가?
- 검증 함수들이 어떤 것은 `boolean`, 어떤 것은 `{ ok, reason }`을 반환하지 않는가?
- 함수 이름이 표준 라이브러리나 프로젝트의 기존 추상화와 충돌해 실제 계약을 오해하게 만들지 않는가?

### 적합한 개선

- 계산·조회와 명령·부수 효과를 분리하거나, 이름에 `save`, `track`, `withAuth` 같은 동작을 명시한다.
- 같은 종류의 함수·Hook에 일관된 반환 계약을 적용하고, 필요하면 `{ ok: true } | { ok: false; reason: string }` 형태로 좁힌다.
- 호출부가 실제 동작을 이름만 보고 선택할 수 있게 한다.

### 피할 개선

- 부수 효과를 삭제해 기능을 없애기
- JSDoc만 추가해 숨은 동작을 그대로 두기
- 기존 공개 API를 깨면서 타입 일관성만 맞추기

## 3. 응집도

### 확인할 것

- 한 기능 수정에 여러 기술별 디렉터리를 동시에 찾아가야 하는가?
- 함께 변경되는 상수·타입·검증·API·UI가 서로 멀리 떨어져 있는가?
- 같은 의미의 값이 여러 파일에서 따로 선언되어 한쪽만 바뀔 수 있는가?
- 폼의 변경 단위가 필드인지 전체 흐름인지에 비해 검증·상태·제출 로직의 위치가 어긋나는가?

### 적합한 개선

- 함께 바뀌는 코드를 도메인·기능 경계 가까이 배치한다.
- 실제로 같은 계약을 공유하는 값만 하나의 상수·모듈로 둔다.
- 독립 검증·재사용이 중요한 폼은 필드 단위로, 필드 간 의존·단계 흐름이 중요한 폼은 폼 전체 단위로 묶는다.

### 피할 개선

- 관련 없는 코드를 하나의 거대 파일에 모으기
- 짧은 우연한 중복까지 공유 모듈로 만들기
- 디렉터리 깊이만 늘리고 변경 단위를 개선하지 않기

## 4. 결합도

### 확인할 것

- **Props Drilling**처럼 중간 컴포넌트가 사용하지 않는 Props를 여러 계층에 전달하는가?
- 하나의 Hook이 서로 다른 상태·이벤트·데이터 소스를 모두 관리하는가?
- 공통 Hook·컴포넌트의 작은 수정이 여러 페이지의 서로 다른 요구사항을 깨뜨릴 수 있는가?
- 한 기능을 수정할 때 관련 없는 기능의 인터페이스까지 바꿔야 하는가?

### 적합한 개선

- 중간 계층이 전달만 하는 값은 조합(`children`)으로 바꾸고, 깊고 실제로 공유되는 상태에만 Context를 검토한다.
- Hook을 도메인 책임별로 나누되, 소비자와 테스트가 실제로 분리되는지 확인한다.
- 페이지별 동작이 달라질 가능성이 있으면 중복을 허용해 변경 폭을 줄인다.

### 피할 개선

- 모든 Props를 전역 상태·Context·Redux로 옮기기
- 하나의 거대한 “스마트 컴포넌트”에 로직을 집중하기
- 공통화를 유지하려고 옵션·플래그를 계속 추가하기

## 기준 간 트레이드오프

- 추상화와 공통화는 함께 바뀌어야 할 코드의 응집도를 높일 수 있지만, 읽어야 할 간접 계층을 늘려 가독성을 낮출 수 있다.
- 중복은 응집도를 낮출 수 있지만, 페이지별 변경이 서로 영향을 주지 않게 해 결합도를 낮출 수 있다.
- 폼·Context·공통 Hook의 최적 경계는 고정 규칙이 아니라 실제 변경 단위·재사용성·필드 의존성으로 결정한다.
- 리뷰에서는 “어떤 기준이 더 좋다”가 아니라, 현재 위험과 앞으로 함께 변경될 가능성에 근거해 우선순위를 설명한다.
