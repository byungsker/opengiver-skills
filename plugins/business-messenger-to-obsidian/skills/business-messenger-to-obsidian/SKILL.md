# 업무 메신저 → Obsidian 히스토리

업무 메신저의 대화, HTML export, PDF, 텍스트 붙여넣기 또는 캡처에서 확인되는 업무 흐름을 사용자가 지정한 Obsidian vault에 표준 형식으로 기록한다. 결과물은 인수인계를 위해 읽는 한글 문서이며, 원본 export 폴더나 작업용 workspace에 결과 문서를 두지 않는다.

## 적용 범위

다음 요청에 적용한다.

- 업무 메신저 대화의 기간별 업무 정리
- 휴직·복직 또는 인수인계를 위한 프로젝트 히스토리 작성
- 대화에서 사람별 작업, 사용자의 언급, 현재 진행 과업과 일정 추출

단순 대화 요약이나 사적인 대화 정리는 이 스킬의 범위를 벗어난다.

## 저장 위치

사용자가 지정한 vault 루트를 먼저 확인한다. 지정하지 않았으면 저장 전에 질문하고, 개인 계정·iCloud·로컬 경로를 추측하지 않는다. 프로젝트·팀 하위 경로도 사용자가 정한 위치를 따르며, 기존 프로젝트 노트가 있으면 먼저 찾아 중복 생성을 피한다. 원본 메시지 export 폴더와 workspace에는 최종 문서를 생성하지 않는다.

## 고정 문서 형식

반드시 [references/template.md](references/template.md)의 frontmatter와 섹션 순서를 그대로 사용한다. 섹션을 삭제하거나 순서를 바꾸지 않는다. 근거가 없는 섹션도 삭제하지 않고 `확인되지 않음`으로 채운다.

본문의 세부 정보는 고정 표로 정리한다.

1. 월별 업무 정리 표: 월, 핵심 변화, 주요 작업, 담당·협업, 상태·남은 일
2. 담당자별 업무 정리 표: 담당자·표시명, 기록상 역할, 확인되는 작업, 기간, 주의점
3. 현재 진행 과업 일정 표: 과업, 시작 확인 시점, 진행 내용, 약속된 종료·마감, 마지막 상태
4. 사용자 언급 여부 표: 날짜, 직접 발신·본문 언급 구분, 내용, 해석
5. 특정 프로젝트·기능 별도 추적 표: 시점, 기록된 일, 상태

표 앞뒤의 결론과 해석은 짧은 문단으로 쓴다. 본문을 긴 불릿 목록으로 대체하지 않는다. 제품명·저장소명·API명·오류 코드는 원문 표기를 유지하되, 설명은 한글로 쓴다.

## 사실 추출 규칙

- 월별 표는 source cutoff 안의 메시지만 사용한다. 날짜가 명시된 경우에만 날짜를 기록한다.
- 과업 시작일은 최초 요구사항·기능 정의·작업 착수 메시지 중 가장 이른 확인 시점을 적는다.
- 종료일은 대화에 명시된 약속·계획만 적는다. 추정한 기한은 쓰지 않고 `미정`으로 표시한다.
- `예정`, `배포`, `테스트 완료`, `오픈`은 당시 대화의 상태로 기록하고, 현재 운영·고객 승인·실제 오픈으로 승격하지 않는다.
- 발신 표시명과 본문에서 언급된 사람을 분리한다. 표시명만으로 공식 이름·직책·계정 소유·현재 담당자를 확정하지 않는다.
- 사용자의 직접 발신이 없더라도 본문에 사용자가 언급되었는지 별도 검색하고, 직접 발신 증거와 본문 언급을 다른 행으로 기록한다.
- 사용자가 만든 프로젝트라고 알려준 경우 별도 프로젝트 섹션에서 그 맥락을 보존하되, 현재 소유권은 별도 확인 대상으로 둔다.
- source cutoff 이후의 실제 상태는 `2026-09-02 현재 확인되지 않음`처럼 명확히 표시한다.

## 개인정보와 보안

원문 메시지 전체, 계정·이메일, 고객 데이터, private URL, 토큰, 비밀번호, API key, credential, `.env` 파일의 내용은 결과 문서에 복사하지 않는다. 필요한 경우 `[비공개]` 또는 안전한 요약으로 바꾼다. `.env`와 secret-like 첨부는 열지 않고 존재 사실만 기록한다.

## 실행 흐름

1. 사용자가 준 원본의 형식·기간·채널·파일 범위를 확인한다.
2. source cutoff와 실제 확인 가능한 sender display name을 정한다.
3. 월별 변화, 담당자별 작업, 과업 일정, 사용자 언급, 특정 프로젝트를 각각 추출한다.
4. 고정 템플릿으로 한글 문서를 지정된 vault에 생성하거나 기존 문서를 갱신한다.
5. 표의 날짜·담당·상태·종료일을 원본과 대조하고, 불확실성은 표 안에 남긴다.
6. 필요하면 이 스킬의 재사용 결과를 LLM Wiki의 concept·entity·query에 승격한다. Wiki 완료를 주장할 때는 canonical runner의 health gate가 100%인지 확인한다.

## 완료 기준

문서는 사용자가 지정한 vault 하위 경로에 있고, 고정된 5개 표와 별도 프로젝트 섹션, 증거 주의점, 문서 맨 끝의 현재 진행 과업 표를 포함해야 한다. 현재 진행 과업 표는 항상 문서의 마지막 섹션이어야 한다.
